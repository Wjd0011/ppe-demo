## 一、对照已有方案，创新点在哪里

先把"已有方案"摆清楚，否则"创新"是自说自话。

| 已有方案的典型形态 | 它做到了 | 它没做的（本项目的切入点） |
|---|---|---|
| ultralytics 训练脚本 + `predict.py` 推理 demo（GitHub 上 PPE 项目绝大多数） | 训练一个能出框的模型，报一个 mAP | 只报"整图单尺度"一个数；不做推理策略对照；不做"人级合规"结论 |
| 商用 PPE 平台（海康、旷视等） | 端到端可用、实时告警 | 不公开权重、不公开失败案例、不可复现 |
| X-AnyLabeling / Label Studio 等标注工具 | 人工标注 + 预标注 | 不提供"预标注到底省了多少人工"的量化 |

本项目的三个创新点，都是**针对上面那张表的空档**做的，而且都带对照实验。

### 1. 双尺度联合推理：同一份权重，靠推理策略把 mAP 提上去

不做训练微调（没有 CUDA、没装 torch），只在推理端改一件事：把整图跑一遍，再把图缩到 0.5× 跑一遍，两套预测按 `fx, fy` 反算回原图坐标后按类合并做 NMS。

| 策略 | mAP@50 | mAP@50-95 | 框/图 | 耗时 | 相对基线 |
|---|---|---|---|---|---|
| A · 整图基线 | 0.5401 | 0.2212 | 9.57 | 43 ms | — |
| **B · 缩图多尺度（采用）** | **0.5819** | **0.2319** | 10.37 | 90 ms | **+0.0418**（相对 +7.7%） |
| C · 分块 2×2（负面对照） | 0.2613 | 0.0817 | 15.11 | 184 ms | −0.2788 |

**为什么这算创新而不是调参**：它给出了一个反直觉的、可证伪的结论。
社区里"小目标检测不好就把图切块放大"是主流直觉，本项目用 C 组把它证伪了——分块后每块被强制放大回 640，尺度分布偏离训练分布，**大目标召回从 0.7392 腰斩到 0.4608**，整体 mAP 掉一半。
真正有效的是反方向：**缩图**。缩图让每个目标在 640 输入里占的像素变多，大中目标判得更稳。

按目标边长拆开看召回，才看得到这个改动的真实作用点：

| 策略 | 小 <48px | 中 48–96px | 大 ≥96px |
|---|---|---|---|
| A | 0.7733 (58/75) | 0.7647 (117/153) | 0.7392 (292/395) |
| B | 0.7733 (58/75) | 0.7712 (118/153) | **0.8025 (317/395)** |
| C | 0.8000 (60/75) | 0.6928 (106/153) | 0.4608 (182/395) |

并且做了**第二划分复核**，避免"测试集偶然"：验证集 119 张 A 0.5696 → B **0.6201**（+0.0505），大目标召回 0.7715 → 0.8344。两个划分方向一致。

**诚实边界（写进 README 的）**：B 不是免费的——耗时 43→90 ms 接近翻倍；B 也**没有**改善小目标（0.7733 → 0.7733，一点没变）。说"多尺度能看见小目标"就是造假。

### 2. 人级包含判定：输出"谁缺帽子"，不是一堆框

框级检测回答"图里有几个安全帽框"，业务要回答的是"这张图里几个人不合规、各缺什么"。
本项目在推理后加一层规则：一个 PPE 框（安全帽 / 反光背心）若与被检测人框的**交叠面积占该 PPE 框面积 > 25%**，则判定"这个人戴了/穿了"；否则计入违规，并记录缺的是"安全帽"还是"反光背心"。

这一点直接可验证：用 `demo`（32 张）和 `demo2`（60 张）里已有的 JSON 标注（不是模型预测）复算人级合规，得到可展示的分布：

| 子集 | 张数 | 全合规 | 仅缺安全帽 | 仅缺反光背心 | 两项都缺 | 无「人」框 |
|---|---|---|---|---|---|---|
| demo | 32 | 7 | 2 | 11 | 12 | 0 |
| demo2 | 60 | 9 | 6 | 18 | 24 | 3 |

**边界也写清楚了**：这是"面积占比包含关系"，不是"人-帽配对"。人群密集时会张冠李戴（A 的帽子算到 B 头上），第六节的 6 张最差样本里就有两例。下一步才上 IoU 矩阵 + 匈牙利匹配。

### 3. 零 torch、零 CUDA 的全链路自实现

`requirements.txt` 只有四个包：`numpy / onnxruntime / opencv-python-headless / pillow`，合计约 120 MB。

对照：ultralytics 官方全家桶带 torch（CPU 版）约 2 GB 起。本项目从预处理到评估全部手写：

| 环节 | 常见做法 | 本项目 | 位置 |
|---|---|---|---|
| letterbox 缩放填充 | ultralytics `LetterBox` | 手写 15 行 | `tools/yolo_onnx_predict.py:63` |
| 坐标反算 | ultralytics 内部 | 手写 `(x-dx)/ratio` | `tools/yolo_onnx_predict.py:130-134` |
| NMS | torchvision / ultralytics | 手写 numpy | `tools/yolo_onnx_predict.py:75` |
| mAP（101 点插值） | pycocotools | 手写 numpy | `tools/eval_vs_gt.py:85` `voc_ap` |
| A/B 实验框架 | 无 | 手写 3 策略 + 召回分桶 | `tools/ab_tiled.py` |

**为什么这算创新点**：它把"能不能在没有 GPU 的教室电脑上 13 分钟复现全部数字"变成了可交付事实（`python run.py --all`，CPU）。

## 二、作品价值用处在哪里

价值分三层，每层都有对应的可检查产物。

### 1. 方法价值：一套可复现的"推理策略对照"范式

大多数检测项目交付的是"一个模型"，本项目交付的是**一个对照方法**：
- 同一份 ONNX 权重、同一份测试集，只改推理策略，跑三组（整图 / 缩图多尺度 / 分块）；
- 不只看总 mAP，还按目标边长分桶看召回，定位改动到底救了谁；
- 换第二个划分（验证集 119 张）复核方向，排除偶然。

这个范式可以直接搬到任何"固定输入尺寸的检测模型"上，用来回答"我的后处理到底有没有用"。

### 2. 资产价值：可直接用的检测能力

| 资产 | 文件 | 规格 |
|---|---|---|
| 预训练检测权重 | `models/construction_ppe_yolov8n.onnx` | 12,245,828 B，10 类，CC BY 4.0 |
| 本项目训练产物 | `models/demo_trained_yolov8n.onnx` | 12,750,066 B，5 类，8 轮 CPU 训练 |
| 标注软件接入配置 | `models/ppe_yolov8n.yaml`、`models/ppe_demo_trained.yaml` | 中文类别 + `filter_classes` 只报 5 类 |
| 已标注演示集 | `demo/`（32 张）、`demo2/`（60 张） | JSON 框 599 + 547 = 1146 个 |
| 全量数据划分 | `train/ valid/ test/` | 997 / 119 / 90 张，标注 6386 / 715 / 623 |
| 训练证据 | `docs/demo_train_results.csv`、`docs/demo_train_args.yaml` | 逐轮 8 行指标 + 超参数快照 |
| 答辩材料 | `docs/PPE答辩汇报-最终版.pptx`、`web/index.html` | 17 页 PPT + 12 节静态网页 |

### 3. 使用价值：三个真实场景

| 场景 | 怎么用 | 增益 |
|---|---|---|
| 安全巡检照片批量筛查 | `python tools/yolo_onnx_predict.py --images <目录> --json out.json --save-vis` | 90 张 53 ms/图，纯 CPU，笔记本就能跑；输出每张的违规名单 |
| 标注预填（省人工） | X-AnyLabeling 里 `Ctrl+B` 批量自动标注 | 92 张演示图里机器已给 1146 个框，人工只做增删 |
| 课堂 / 答辩演示 | 双击 `web/index.html`（离线静态） | 32 张三视图 + 6 张最差样本，可切"原图 / 真值 / 预测" |

### 4. 反面价值：把"不能干什么"量化了

`README.md` 的"适用范围"表不是免责声明，是有实验支撑的：
- 夜间 / 强逆光 / 浓雾 → 不适用（失败样本里有逆光漏检）；
- 目标边长 < 16 px → 不适用（小目标召回 0.7733 且不随策略改善）；
- 人群密集（>8 人同框）→ 会张冠李戴（`ppe_0357` 漏「人」4 个、误检「未穿背心」8 个）；
- **不做实时告警、门禁联动、替代人工验收**。

## 三、怎么实现

### 3.1 数据与权重（外部输入，可追溯）

| 项 | 内容 |
|---|---|
| 数据 | Roboflow Universe `construction-safety-gsnvb`，**CC BY 4.0**，1206 张真实工地照片，YOLO 格式 |
| 下载路径 | `hf-mirror.com/datasets/LibreYOLO/construction-safety-gsnvb`（本机到 HF 官方域名全部超时） |
| 类别 | `0 helmet 1 no-helmet 2 no-vest 3 person 4 vest`（`data.yaml`） |
| 权重 | Hugging Face `mancalazure/construction-ppe-safety`，**CC BY 4.0**，YOLOv8n 在 Roboflow `construction-site-safety v28` 微调 |
| 权重指纹 | ONNX opset 12，12,245,828 B，SHA256 `1D5F3CF69883E89BA6E2B3836A0B21623044E9A682F1F00DFBACAC97B99BAF94` |
| 划分 | 997 / 119 / 90，标注框 6386 / 715 / 623 |

### 3.2 推理链（`tools/yolo_onnx_predict.py`）

```
读图  imread_unicode:63   cv2.imdecode(np.fromfile(path, np.uint8), IMREAD_COLOR)
      ↓ 中文路径必须这么读，cv2.imread 在 Windows 上直接返回 None
letterbox:63              等比缩到 640，灰边 114，返回 (pad, ratio, dx, dy)
      ↓
预处理                    BGR→RGB → HWC→CHW → /255.0 → float32 → [1,3,640,640]
      ↓
onnxruntime CPU           输出 (4+nc, 8400)，nc=10
      ↓
解码:112-120              cls_scores = out[4:] → max(axis=0) 取分数、argmax 取类别
                          掩码 score > conf(0.35)
      ↓
反算:130-134              cxcywh → xyxy → (x-dx)/ratio → clip 到原图边界
      ↓
NMS:75                    IoU 0.45，按类分别做
      ↓
输出                      [{xyxy, score, cls_id, name}]，name 走 CLASSES 10 项表
```

### 3.3 双尺度（`tools/ab_tiled.py:96` `detect_multiscale`）

```
原图 ──┬── 整图 → letterbox 640 → detect → 框坐标 (fx=1, fy=1)
       └── 0.5× resize(INTER_AREA) → letterbox 640 → detect → 框 ×(fx, fy) 反算回原图
                                    ↓
                       按 cls_id 分组 → 每组内合并 → NMS(0.45)
```

关键代码（`tools/ab_tiled.py:114`）：`fy, fx = h / view.shape[0], w / view.shape[1]`——两个尺度的框必须先回到同一个坐标系才能合并，漏了这步两套尺度就无法合并。

### 3.4 评估（`tools/eval_vs_gt.py`）

```
pred_test.json + test/labels/*.txt
   ↓ iou_matrix:38           预测框 × 真值框 的 IoU 矩阵
   ↓ 按 score 降序贪心匹配     IoU ≥ 0.5（AP@50）或多阈值 0.5:0.05:0.95（AP@50-95）
   ↓ voc_ap:85               101 点插值 PR 曲线下面积
   ↓ 每类 AP 求均值           → mAP@50 = 0.5401 / mAP@50-95 = 0.2212
```

### 3.5 人级合规（`tools/yolo_onnx_predict.py:187` `compliance`）

```python
# 逐个「人」框，检查是否有帽子/背心框落在里面
inter / PPE框面积 > 0.25  →  算这个人戴了/穿了
否则 → 记违规，missing 里写明缺「安全帽」还是「反光背心」
```

### 3.6 训练链路（本项目唯一一次训练，`docs/全链路操作手册.md` 第 4 节）

| 参数 | 值 |
|---|---|
| 入口 | X-AnyLabeling → `Train` → `Ultralytics` 三页签 |
| Environment | 装了 torch + ultralytics 的 `python.exe` |
| Model | `weights\yolov8n.pt`（6.5 MB 起点） |
| Data | `data.yaml`（省略 `path`，以 yaml 所在目录为根） |
| Device / Epochs / Batch / imgsz / Workers / Fraction | cpu / 8 / 8 / 416 / 2 / 0.25 |
| 耗时 | 272.532 s（8 轮累计） |
| 末轮 | mAP50 **0.71675**、mAP50-95 0.39413、P 0.677、R 0.689 |
| 导出 | ONNX 1.0 s，12,750,066 B，输入 `[1,3,640,640]`，输出 `[1,9,8400]` |
| 接回 | 自动进模型下拉框，实测 48 ms/图 |

逐轮轨迹（`docs/demo_train_results.csv`）：0.41714 → 0.5041 → 0.56324 → 0.64229 → 0.67203 → 0.6501 → 0.68427 → **0.71675**。

**注意**：这个 0.7168 是「416px / 25% 数据 / 8 轮」在**验证集**上的快速演示值，和主实验的 0.5401（640px、全量、测试集、10 类权重）**不是同一口径，不能对比**。它的作用是证明"标注 → 训练 → 导出 → 接回"这条链路能跑通。

### 3.7 一键复现（`run.py`）

```powershell
uv venv .venv --python 3.12
uv pip install -r requirements.txt
python run.py --all          # 六步，CPU 约 13 分钟
```

`STEPS`（`run.py:33`）与 `ORDER`（`run.py:61`）：`infer → eval → ab → painting → failures → web`，每步都 shell out 到 `tools/` 下对应脚本，页面上每个数字都能追到一条真跑过的命令。

### 3.8 踩过的坑（都已修，写进文档）

| 坑 | 现象 | 处理 |
|---|---|---|
| 中文路径 | `cv2.imread` 返回 None，全部图"读不出来" | 全仓改 `cv2.imdecode(np.fromfile(...))` |
| `classes.txt` 带 BOM | 导出 YOLO 标注后类别名首字符是 BOM，全部丢框 | UTF-8 **无 BOM** 重写 |
| 模型 yaml 带 BOM | PyYAML 读出 `\ufeff安全帽`，该类静默匹配失败 | 同上，无 BOM |
| XAL 读 yaml 用系统编码 | 中文 Windows 下 GBK 解码 → `UnicodeDecodeError` | 给 `anylabeling/services/auto_labeling/model.py:122` 的 `open()` 补 `encoding="utf-8"` |
| 类别索引 | ONNX 输出通道固定 10 项，少写一项后面全错位 | `classes` 保持 10 项，用 `filter_classes` 只报 5 类 |
| 硬编码绝对路径 | 换台机器全部失效 | 全仓改相对路径 / `%USERPROFILE%` / 环境变量（详见 `docs/文件索引.md`） |

### 4.2 用 YOLO 的真实体验（好和不好的都说）

**好的部分**

1. **YOLOv8n 这个小模型在 CPU 上就已经够用**：6.5 MB 权重，640 输入，ONNX Runtime 单核多线程跑 43 ms/图。教室笔记本能演示。
2. **预训练权重开箱可用，不用自己训**：`construction-ppe-safety` 直接给出 0.5401 mAP50，省掉了标注 + 训练的全部门槛。
3. **ONNX 导出极快、兼容性好**：1.0 秒导出，opset 12，`onnxruntime` CPU provider 直接吃，不用装 torch 也能推理。
4. **X-AnyLabeling 把训练做成了 GUI**：`Train > Ultralytics` 三个页签填完就跑，272 秒出 0.72 的模型，还能一键导出并**自动接回**自动标注的下拉框——这条"标注→训练→导出→接回"闭环是 YOLO 生态真正好用的地方。
5. **输出格式固定好解析**：`(4+nc, 8400)`，前 4 行是 cxcywh，后面是逐类分数，写 30 行 numpy 就能解完。

**不好的部分（这些才是真体验）**

1. **官方推理栈太重**：`ultralytics` + `torch` 起步 2 GB，为了跑一个 12 MB 的 ONNX 装 2 GB 依赖，不划算。这正是本项目手写 300 行推理的原因——装 4 个包（约 120 MB）就够了。
2. **YOLO 救不了数据不平衡**：`no-helmet` 测试集只有 24 个框（3.9%），AP 只有 0.275；训练集 997 张里也只有 94 个（1.4%）。换更大的模型、加更多轮次都没用，只能补数据。
3. **框级检测没有"关系"**：YOLO 只给框，不给"这个帽子属于这个人"。人多的时候人框和帽子框错配，业务上就是误判。这一层必须自己写后处理。
4. **固定 640 输入限制了"放大"**：ONNX 图是死的，想让远处的人变大只能**缩图**（让目标占更多像素比例），不能真放大。社区里"切块放大救小目标"的做法在本模型上直接翻车（mAP 0.5401 → 0.2613）。
5. **预训练权重的类别是死的**：`construction-ppe-safety` 有 10 类（含口罩、锥桶、机械、车辆），我们只要 5 类。不能删 `classes`（会错位），只能靠 `filter_classes` 过滤。
6. **中文环境全是编码坑**：路径要 `imdecode`、`classes.txt` 和 yaml 都不能带 BOM、XAL 读 yaml 要手动补 `encoding="utf-8"`。这些坑没有任何一处是 YOLO 文档里写的。

**一句话总结体验**：YOLO 给的是一个**能用的基线**（出框、可训练、可导出），但离**能交付的系统**还差三块——人级语义、数据不平衡、部署体积。本项目的三个创新点正好填这三块，这也是它比"又一个 YOLO 推理 demo"多出来的东西。
